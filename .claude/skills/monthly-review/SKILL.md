# 月次PDCAレビュー手順

暗号資産モメンタムbotの成績を月1で評価し、次の一手を1つ提案する。**新規セッションでも実行可能**（必要な文脈は全てファイル/エンドポイントにある）。**売買・設定変更は行わない＝助言のみ**（[[trading-ops]] の不変ルール）。

## 0. 前提を読む（最初に必ず）
1. `trading-ops` skill を読む（仕組み・不変ルール・データの取り方・落とし穴）。
2. `CHANGELOG.md` を読む（いつ・何を・なぜ変えたか／前回レビューの仮説とレビュー日）。
3. `reviews/` の前回レビュー（あれば）を読む（前回の宿題・仮説の答え合わせ）。

## 1. データを集める（公開データ中心＝合言葉なしでも可）
- `data/perf_log.csv` … 日次の nav（戦略NAV指数）/ regime_up / regime_distance_pct / index / btc_jpy / held / targets。**これが主データ**。
- `GET /snapshot?public=1`（合言葉不要）… 現在の地合い・保有・上位候補・BTC。`?cb=<変化値>` でWebFetchの15分キャッシュを回避。
- 必要なら bitbank公開日足でベンチ補完。
- ※実現損益(¥)や残高は `/tax`・`/snapshot`(要合言葉)にあるが、合言葉が無いセッションでは扱わない。**レビューは NAV・%・地合い（非機微）**中心で成立させる。金額(¥)はレポートに書かない（公開リポに残すため）。

## 2. 評価する（Check）
perf_log.csv の nav 系列（今月分＋全期間）から：
- **リターン**：今月のNAV変化%、全期間のNAV（start=100基準）。
- **ベンチ対比**：同期間の BTC（btc_jpy を100正規化）と比較。「戦略はBTC買い持ちに勝っているか」。
- **ドローダウン**：最大DD・現在DD（`app/equity.py` の drawdowns と同じ考え方＝ピークからの下落率）。
- **地合いフィルターの効き**：regime_up=false（現金退避）だった日に、指数(index)やBTCが下げていたか＝退避は損失回避に役立ったか。逆に、オフで取り逃した上昇は無かったか。
- **picks（銘柄選定）**：held と targets、月内のローテーション。上位候補が実際に伸びたか（index/BTC比）。
- **異常**：perf_log の日付欠損、regime列が空の期間、極端な book_ret_pct、CHANGELOGにある直近変更の影響。

## 3. 提案する（Act）※助言のみ
- **一度に1変更**の原則。変えるなら「何を・いくつに・なぜ・いつ結果を見るか（レビュー日）」を1つだけ提案。少額でないので過剰最適化を避け、大崩れしない設計を優先。
- 変更不要なら「据え置き」と明記（それも立派な結論）。
- 候補例：地合いフィルター閾値、保有数(CRYPTO_MOM_TOP)、上昇率の計測期間(CRYPTO_MOM_LOOKBACK)、エクスポージャー(ORDER_SIZE_PCT)、DDアラート水準(DD_ALERT_PCT)。**提案するだけ**で、適用はユーザーが判断・実行する。

## 4. レポートを残す
- `reviews/REVIEW-YYYY-MM.md`（当月）に、簡潔に：
  - サマリー（今月NAV%・全期間NAV・BTC対比・最大DD/現在DD・地合いの状況）
  - 良かった点／気になる点／異常の有無
  - **次の一手（1つ）**：仮説・変更内容・レビュー日、または「据え置き」
- **金額(¥)は書かない**（非機微のNAV・%・地合いのみ＝公開リポに安全に残す）。
- CHANGELOG に1行追記（例：`## YYYY-MM-DD 月次レビュー：<結論> → 提案:<1つ> レビュー日<日付>`）。
- 変更を commit（可能なら push）。**発注・設定変更のAPI/ボタン操作は絶対にしない。**

## 5. ユーザーへの報告
- 3〜6行で要点：今月の成績（NAV/ベンチ対比/DD）、地合いの状況、次の一手（1つ or 据え置き）。
- 判断が要る提案は、ユーザーが決められるよう「なぜ・効果・リスク」を短く添える（投資助言はしない・最終判断は本人）。
